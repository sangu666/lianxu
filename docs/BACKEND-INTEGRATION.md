# 第四步：页面与数据库接入

## 现在可以使用

在 E:\lianxu 执行 `npm run backend:local`，打开 **http://127.0.0.1:3100/**。页面和 API 共用来源，无需另外启动前端，也不启用跨域访问。地址使用 127.0.0.1；localhost 是另一来源，不能混用 Cookie 和来源校验。

1. 点击页面上方“登录 / 注册”，使用邮箱和至少 12 个字符的密码注册。
2. 到“身体与资料”填写并保存，数据库建立资料及第一份规则计划。新账户显示的初始值是虚构示例，需要自行核对。
3. 在“训练计划”替换动作、编辑目标或确认外部 JSON 草稿，保存后建立新版本。
4. 到“训练记录”开始训练，录入、编辑、删除组，修改日期与备注，完成或删除训练。刷新后恢复数据库记录。
5. 到“进展回顾”保存体重；同日更正需与页面读取的原记录一致。
6. “动作资料库”通过数据库分页、搜索和筛选，点击后按需读取文字详情。
7. 退出清除当前会话；重新登录恢复同一账户记录。不要忘记当前没有密码找回。

数据库是本机 PostgreSQL，不是已部署的云服务。训练与饮食仍为规则/演示，没有真实 AI；照片仅临时预览，不上传。全库计划选择器仍保留轻量静态编号索引，用于即时选择及共享草稿校验；大体积动作说明通过数据库读取。

## 原浏览器记录

登录后不扫描、不自动上传原 localStorage。账户事实记录使用数据库；第六步仅将未完成操作暂存到当前浏览器的账户专属队列，不保存令牌、照片或密码，见 BACKEND-RELIABILITY.md。未登录为浏览器模式；原 3002 静态预览也继续支持原存储方式。不同来源的浏览器记录分开保存，退出账户后看到的是当前来源的浏览器记录。

账户备份可以导出；第 5 步现已提供独立的旧备份迁移入口，先预览再显式确认，详见 [迁移说明](BACKEND-IMPORTS.md)。浏览器模式的完整恢复与账户迁移使用不同入口，不自动上传或覆盖原浏览器资料。

## 写入与冲突

页面先构造候选状态，等待接口成功后才更新当前状态，失败保留表单输入。资料、计划和训练分别在事务中保存；训练动作的编号、名称、单位和目标快照不可修改，实际组可以更正。旧计划版本只新增，不更新。

| 操作     | 接口                    | 冲突依据                                                                 |
| -------- | ----------------------- | ------------------------------------------------------------------------ |
| 保存资料 | PUT /me/profile         | expectedRevision；页面额外带 expectedVersion，防止旧资料页覆盖刚改的计划 |
| 确认计划 | POST /me/plans          | expectedVersion + expectedRevision；只能使用服务端当前账户资料           |
| 保存训练 | PUT /me/workouts/:id    | expectedRevision，创建为 0，更新带读取的版本；每次成功递增               |
| 删除训练 | DELETE /me/workouts/:id | expectedRevision；级联删除当次动作和组                                   |
| 保存体重 | PUT /me/weights/:date   | expected 为 null 或读取的 {id, kg}；同日多条历史记录不自动合并           |

训练创建校验当前数据库计划，并拒绝客户端伪造动作目标、旧版本或直接导入归档；每账户最多一个进行中训练。训练组和体重千克数值最多三位小数，超精度拒绝，不静默舍入。体重记录沿用现有页面一天一个值的交互，未来迁移遇到同日多次测量需专门处理。

资料保存返回 profile、revision、planVersion、snapshot；计划保存返回 version、snapshot。账户页面展示数据库保存的 days，不因未来规则代码变化重新解释旧版本。读取新增 GET /me/workout-records 分页完整训练；原摘要与详情接口继续可用，避免刷新时每条训练单独请求。

客户端携带 HttpOnly Cookie、内存 CSRF 和 X-Account-Id。账户归属仍由服务端会话决定；X-Account-Id 仅检测另一标签页切换账户，不能授予权限。版本冲突、过期或切换提示刷新重新核对，不能自动覆盖重试。第六步已实现请求编号、成功回执和待同步队列。响应丢失后用原编号重试，再重新读取账户事实；版本冲突仍停止并要求核对，见 BACKEND-RELIABILITY.md。

## 验证和学习

执行 `npm run check`、`npm run format:check`、`npm run test:backend`。后端测试使用独立真实 PostgreSQL 和虚构账户，不连接个人开发数据。新增集成测试通过实际路由调用前端客户端，验证资料、计划、训练、体重、版本冲突、账户切换及静态资源访问边界。

阅读顺序：

1. `public/account-view.js`：登录表单、等待与错误提示，密码只提交到账户接口。
2. `public/account-api.js`：分页读取、十进制映射、一次操作一个事务、失败不覆盖状态。
3. `public/app.js` 的 commitState：浏览器/账户模式分开，保存成功后统一刷新事实状态。
4. `server/write-routes.ts`：账户锁、版本检查、不可变快照和训练组事务。
5. `server/private-routes.ts`：只读记录字段白名单、分页及资料保存。
6. `server/test/integration.test.ts` 与 `test/account-api.test.js`：用行为验证持久化和失败边界。

本轮第五个数据库迁移仅更新已经实现的 revision 与 snapshot 中文说明，表和字段仍为 10 张 / 73 个，没有新增健康数据字段。源码尚未同步 GitHub。
